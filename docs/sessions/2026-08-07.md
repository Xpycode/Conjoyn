the parser about *filenames* and never inspects the containing folder's name, and `resolveMediaFolders`

GoPro-only-card resolve test instead of inventing a fix for a gap that doesn't exist.

**The real finding: G0's hazard has a mirror image, and this wave armed it.** `family` is non-Optional
(every clip has one), so a *synthesized* encoder would write `"family":"dji"` into every DJI clip on
disk — the overwhelming majority — changing the shape 1.0.4 wrote and breaking G0.1's pinned key set.
The fix is a hand-written `encode(to:)` that omits the `.dji` default, keeping a DJI clip byte-identical
while a GoPro clip writes its family explicitly. But hand-writing the encoder trades G0's `keyNotFound`
hazard for its opposite: **a field added to `CodingKeys` and to `init(from:)` but forgotten in the
encoder is silently never persisted** — it reloads as its default every launch, the queue is subtly
wrong, and *nothing goes red*. Where G0's failure was loud-but-catastrophic, this one is quiet.

Closed it by making `CodingKeys` `CaseIterable` and pinning the encoded key set against `allCases`
(`testEncoderWritesEveryCodingKeyForAFullyPopulatedClip`, in the G0 stop-the-line file where a future
contributor will look). **Verified by reproduction, per the G0 precedent:** injected a `probeFutureField`
key into `CodingKeys` without touching the encoder, watched the test fail naming exactly the missing
key, then reverted and re-ran green. A guard that has never been seen to fail is not a guard.

**Verification discipline.** Every agent claim was re-checked independently rather than taken at face
value: re-ran the full suite myself after each task, diffed the corpus transcription against source,
confirmed `git diff --numstat` showed zero deletions in existing test files, and confirmed

**Tests: 512 → 525, 0 fail.** Merged `--no-ff` to `main` (`8e381e8`); suite re-run green on `main`

## Decisions
- **Fixture cut from recording 6349, not the 6347/6345 the task text named.** The task's *own* rule is
  "pick the lowest-bitrate intact recording", and 6349 is **45 Mbps @ 25 fps** against ~120 Mbps for
  6345/6346/6347/6348 — at 120 Mbps a single 1.04 s GOP is ~11.5 MB, so the pair would have doubled
  the 12 MB cap on its own. Actual total **11.67 MB**. Followed the rule over the example. 6338 stays
  excluded (its ch01 left the archive).
- **The GOP floor is 1.04 s and cannot be cut below under `-c copy`**, so each slice holds exactly
  **one** gpmd packet (telemetry runs at 1 packet/second). Accepted deliberately: the **byte totals**
  carry the assertion weight, not the packet counts. Recorded in the fixture README so the thinness
  reads as a measured floor, not an oversight.
- **`resolveGpmdStreamIndex` compares gpmd *presence*, not index equality** — the index legitimately
  differs between a camera original (3) and a remux (2); only presence disagreement is a real
  layout mismatch.
- **A gpmd layout mismatch is non-retriable**, classified alongside `sourceIdentityChanged`: the
  segments' telemetry presence will not change between attempts.
- **Double-probe cost accepted, not paid down.** A GoPro join probes each segment twice (param guard
  + telemetry index). Folding them together means threading `SegmentStreamInfo` through
  `ensureJoinable`'s signature, which several call sites and tests depend on. Revisit only if GoPro
  join latency becomes noticeable.
- **Next wave set to G3 over the equally-unblocked G5.** G3 is on the critical path to the G8.2 final
  gate: until GoPro chapters actually group, a real recording never reaches the join path from the
  UI, so G4's end-to-end proof cannot be exercised on real footage. G5 hardens a path that already
  works.

## Findings worth carrying forward
- **Finding C reproduced first-hand, and it is worse than "it fails".** `-map 0` on a GoPro source
  errors with *"Could not find tag for codec none in stream #2"* (the tmcd track) and leaves a
  **zero-byte output file**. This is why streams are mapped explicitly — and it bites the *fixture
  cut* too, not just the join.
- **The seam fixtures cannot be camera-original-shaped, which promotes G8.2.** Because ffmpeg cannot
  copy GoPro's source `tmcd`, the cut drops and regenerates it *after* gpmd → fixtures carry **gpmd at
  index 2**, while camera originals carry it at **index 3**. Index 3 is covered by unit tests and by
  the join-time probe but **never end-to-end**. **G8.2 is now the only task that closes that gap** —
  it is no longer merely a final eyeball.
- **The joined output correctly carries a regenerated `tmcd` alongside the preserved `gpmd`** — the
  two data tracks coexist without either being mistaken for the other, which is the `d:0` hazard the
  design avoids by selecting on absolute index.
