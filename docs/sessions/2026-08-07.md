## Progress

**Two questions answered by measurement, not by choosing.**

- **Q1 — is verbatim `gpmd` concatenation semantically correct, or only byte-exact?** Answered
  **yes**, and this was the one genuinely unresolved item in the spec. The earlier session proved
  the bytes concatenate exactly; that says nothing about whether a telemetry consumer can *read*
  the result, because GPMF payloads carry their own internal timestamps that a camera could
  plausibly re-base per chapter. Re-joined the two surviving 25 s seam slices with the proposed
  args using the bundled ffmpeg, extracted the `gpmd` elementary stream, and walked it as raw GPMF
  KLV with a parser written for the purpose:
  - all **50 `DEVC` payloads parse clean, zero desync** — including the one straddling the seam at
    byte 219,220;
  - **`STMP` is recording-relative, not chapter-relative** — chapter 02's first payload reads
    1,536.014 s, continuing chapter 01's clock rather than resetting. Seam step 0.9985 s, identical
    to every other payload gap. *This is the finding*: the feared failure mode can't occur because
    the camera never re-bases the clock;
  - `GPSU` wall clock continuous across the seam (…12:17:56.400 → …12:17:57.400);
  - container packet PTS 0.003 → 49.003 s, 50 packets, every delta exactly 1.000 s.

  So both time sources a consumer can use stay coherent. A *named* third-party tool opening the
  file is still not formally run, but the only two failure modes such a tool could expose — framing
  desync and per-chapter time rebase — are the ones ruled out. Parser checked in at
  `01_Project/scripts/gpmf-dump.py`, because the gpmd verification tests will want it again.

- **Q6 — do cross-month chapter splits happen?** The question rested on a "2026-07 folder holding a
  72nd file". There is no such folder — the user deleted it and its single file the same day.
  Co-location is guaranteed anyway: all chapters share `creation_time`, so the rename workflow
  stamps them identically and files them together. Moot either way.

**Four decisions taken (all as recommended).**

- **Q3 — no absolute split-size constant on the GoPro path.** Grouping rests on chapter numbering +
  stream-param equality + timecode continuity; the watch-folder "expect a continuation" signal
  becomes *relative* (non-final chapters near-equal, final smaller) plus the existing quiet window.
  The decisive evidence against a constant was already in the corpus and had been read as a flat
  band: recording 6349 at 25 fps capped at 10.8471 GiB while the 100 fps recordings capped at
  ~10.718 — it is not a fixed byte count. Add that the Hero 7 in the drawer splits near 4 GB, and a
  Hero 11 constant would be wrong for hardware already owned.
- **Q5 — `DJIClip` gets a hand-written `init(from:)`/`CodingKeys`** with `decodeIfPresent`, not
  Optional-only fields. Optional-only disarms the queue-wipe hazard for exactly one change and
  leaves it armed for whoever adds the next field; the explicit keys are also the mapping the
  deferred DJI→neutral rename will need. Fixed order: **1.0.4-shaped `queue.json` fixture test →
  custom decoder → new fields.**
- **Q4 — the empty-state copy drops the file-size figure** rather than becoming camera-aware. No
  number is true across DJI (~4 GB), Hero 11 (~10.7 GiB) and Hero 7 (~4 GB) at once, and a neutral
  sentence needs no mixed-folder variant.
- **Q2 — ship GX-validated**, GH parsed by symmetry (everything downstream is codec-agnostic), with
  **one ~30 s H.264 clip** owed as a cheap sanity check of GH naming + stream layout. No 11 GB
  chaptered GH capture.

**Gap analysis first, plan second.** Read the actual integration points rather than trusting the
spec's line references: the parser, the grouping core and its `continues()` rules, the merge-arg
builder, the ffprobe stream guard, the verifier's per-stream loop, `CompleteSetGate` and its one
caller, the queue's save/load path, and the two UI copy sites. That surfaced five design questions
the spec had left to implementation — all five were decided during planning and written to
`decisions.md` so they survive the plan being regenerated:

1. **The chapter number rides in the existing `index` field**, and a new `recordingNumber` carries
   recording identity. Two existing consumers read `index` as "position within the recording" —
   `WatchFolderCoordinator.swift:402` picks a group's last segment by highest `index`, and
   `continues()` checks `index + 1` — so mapping chapter there keeps both correct untouched, where
   the more natural-looking mapping (index = file number) would have silently broken the first.
2. **The grouping bucket key becomes `family|variant|recordingNumber`.** Today it buckets on the
   lens-variant suffix, which every GoPro file leaves `nil` — so without this, all GoPro recordings
   would land in one bucket together with the legacy DJI clips.
3. **The gpmd `-map` index is probed from segment 1 at join time**, never read from persisted
   state — the concat demuxer presents the first file's stream layout, and the index differs
   between a camera original (3) and a remux (2).
4. **Nothing selects telemetry as `d:0`.** ffprobe classifies `tmcd` as a data stream too, so the
   obvious selector can resolve to the timecode track — which would produce a *passing* telemetry
   check that verified the wrong stream. Everything selects by resolved absolute index.
5. **A GoPro chain with no timecode on both sides simply doesn't chain** — timecode is the
   continuity signal there (chapters share one `creation_time`), so absent it we split into singles
   rather than guess. All 71 corpus files carry `tmcd`, so it never fires in practice.

**Ordering is the plan's main structural claim.** G0 (the `queue.json` fixture → custom decoder)
blocks every other wave, and the recommended path through the rest is a thin vertical slice —
G0 → parse → probe → **real seam join** — so the two highest technical risks (does `-map 0:<i>`
actually work against the concat demuxer; is the index resolved from the right file) are retired
before grouping, watch-folder gating and copy are built on top of them.

**Caught while planning:** the seam-slice fixture for the real join test cannot be cut from
recording 6338 — its chapter 01 left the volume in yesterday's clear-out. The plan cuts from an
intact group (6347 or 6345) instead, capped at ~12 MB in git.

## Progress

**G0.1 — the fixture is a real blob, not a transcription.** The installed app's own
`~/Library/Application Support/Conjoyn/queue.json` turned out to be exactly what the task needed: 16
jobs written on 2026-07-18, the day 1.0.4 shipped, and `git log` confirms neither `DJIClip` nor

restores, and neither occurs in a queue whose jobs all finished. Checked the bookmark blobs for
identifying data before checking them in (public repo): they carry `/Volumes/2CULL` and nothing from
`/Users`. `QueuePersistenceCompatTests` decodes it with `loadQueue`'s exact decoder config and pins
job/clip counts, paths, exact `CMTime` backings, `streamInfo`, settings, every status case and every
check kind. Green against the unmodified model — which is the point of writing it first.

**The hazard reproduced, and the plan's wording refined.** Before fixing anything, added a probe
field to `DJIClip`: all 10 tests failed with `keyNotFound … Path: [0].clips[0]`, and the app's own
"Failed to load queue" line — the `catch` that discards everything — appeared in the output. But the
*first* probe (`let hazardProbe: Int = 0`) left the suite **green**: Swift omits an immutable
property with an inline default from Codable synthesis entirely. Only `var hazardProbe: Int = 0`
fires it. So the trap is narrower than "any non-Optional field with a default" — and nastier, because
the `let` form looks safe right up until someone changes the keyword.

**G0.2 — hand-written decoder.** Explicit `CodingKeys` for all 13 stored properties;
`decodeIfPresent` for every Optional; plain `decode` only for the six fields that make a clip
meaningless when absent (`id`, `videoFilePath`, `index`, `stem`, duration value + timescale).
`encode(to:)` stays synthesized, so the on-disk shape is byte-identical to 1.0.4's. Verified with the
probe still in place (green → the decoder does its job), then the probe was removed. +3 tests: an
encode→decode round-trip, a missing-keys decode, and one that asserts the **exact key set** a
re-encoded clip produces — the half the fixture can't check on its own, since a new field entering
`CodingKeys` starts appearing on disk and a rollback then has to tolerate it.

**G0.3 — tolerant enums, extended past the task.** `VerificationCheck.Kind` gains an `unknown` case
rather than remapping to a real kind. The plan named only `Kind`, but `SourceTargetResult.Tier` and
`CheckSeverity` are `RawRepresentable` and ride in the same blob, so either one alone defeats the
protection — both got the same fallback. +4 tests, including the end-to-end shape: a foreign check
kind buried in one job's result must not cost the user the other three jobs.

**Suite 495 → 512, 0 fail.** Merged `feature/gopro-g0-persistence` → `main` (`38752f8`), suite re-run
green on `main` after the merge.
