## Progress

**Two questions answered by measurement, not by choosing.**

- **Q1 — is verbatim `gpmd` concatenation semantically correct, or only byte-exact?** Answered
  **yes**, and this was the one genuinely unresolved item in the spec. The earlier session proved
  the bytes concatenate exactly; that says nothing about whether a telemetry consumer can *read*
  the result, because GPMF payloads carry their own internal timestamps that a camera could
  plausibly re-base per chapter. Re-joined the two surviving 25 s seam slices with the proposed
  args using the bundled ffmpeg, extracted the `gpmd` elementary stream, and walked it as raw GPMF
  KLV with a parser written for the purpose:
  - all **50 `DEVC` payloads parse clean, zero desync** — including the one straddling the seam at
    byte 219,220;
  - **`STMP` is recording-relative, not chapter-relative** — chapter 02's first payload reads
    1,536.014 s, continuing chapter 01's clock rather than resetting. Seam step 0.9985 s, identical
    to every other payload gap. *This is the finding*: the feared failure mode can't occur because
    the camera never re-bases the clock;
  - `GPSU` wall clock continuous across the seam (…12:17:56.400 → …12:17:57.400);
  - container packet PTS 0.003 → 49.003 s, 50 packets, every delta exactly 1.000 s.

  So both time sources a consumer can use stay coherent. A *named* third-party tool opening the
  file is still not formally run, but the only two failure modes such a tool could expose — framing
  desync and per-chapter time rebase — are the ones ruled out. Parser checked in at
  `01_Project/scripts/gpmf-dump.py`, because the gpmd verification tests will want it again.

- **Q6 — do cross-month chapter splits happen?** The question rested on a "2026-07 folder holding a
  72nd file". There is no such folder — the user deleted it and its single file the same day.
  Co-location is guaranteed anyway: all chapters share `creation_time`, so the rename workflow
  stamps them identically and files them together. Moot either way.

**Four decisions taken (all as recommended).**

- **Q3 — no absolute split-size constant on the GoPro path.** Grouping rests on chapter numbering +
  stream-param equality + timecode continuity; the watch-folder "expect a continuation" signal
  becomes *relative* (non-final chapters near-equal, final smaller) plus the existing quiet window.
  The decisive evidence against a constant was already in the corpus and had been read as a flat
  band: recording 6349 at 25 fps capped at 10.8471 GiB while the 100 fps recordings capped at
  ~10.718 — it is not a fixed byte count. Add that the Hero 7 in the drawer splits near 4 GB, and a
  Hero 11 constant would be wrong for hardware already owned.
- **Q5 — `DJIClip` gets a hand-written `init(from:)`/`CodingKeys`** with `decodeIfPresent`, not
  Optional-only fields. Optional-only disarms the queue-wipe hazard for exactly one change and
  leaves it armed for whoever adds the next field; the explicit keys are also the mapping the
  deferred DJI→neutral rename will need. Fixed order: **1.0.4-shaped `queue.json` fixture test →
  custom decoder → new fields.**
- **Q4 — the empty-state copy drops the file-size figure** rather than becoming camera-aware. No
  number is true across DJI (~4 GB), Hero 11 (~10.7 GiB) and Hero 7 (~4 GB) at once, and a neutral
  sentence needs no mixed-folder variant.
- **Q2 — ship GX-validated**, GH parsed by symmetry (everything downstream is codec-agnostic), with
  **one ~30 s H.264 clip** owed as a cheap sanity check of GH naming + stream layout. No 11 GB
  chaptered GH capture.
