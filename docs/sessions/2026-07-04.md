## Progress
- User first asked to just **log** the two bugs (screenshots of the Rename popover in light/dark
  mode + a Queue list with truncated names). Logged both to `docs/ideas.md` with exact
  file/line pointers (`RenamePopover.swift:174`, `QueuePanel.swift:262-267`) so a later session
  wouldn't need to re-diagnose.
- User then asked whether they could be fixed now and shipped — answered with a recommendation

  into the next real ship). No code changed at that point.
- User asked to fix properly, `/ultrathink`. Investigated root causes instead of patching symptoms:
  - **Contrast bug:** `Theme.acc1` (`Theme.swift:49`) was a single fixed hex (`0xFFB23E`) explicitly
    documented as "mode-independent," used as *foreground* text/icon color in 22 call sites app-wide
    (not just the Rename popover). Computed exact WCAG relative-luminance contrast from the source
    hex values: **1.63:1** against the light palette's `bg`/`panel`/`panel2` (fails AA's 4.5:1 floor
    badly) vs. **9.38:1** in dark mode — quantifies exactly why it read fine in dark mode but not
    light. Fix: made `acc1` adaptive — `Color(light: 0x8F5600, dark: 0xFFB23E)`, same ~36° hue,
    darkened only for light mode. Verified by reproducing the app's own `NSAppearance`-based
    color-resolution logic in a standalone Swift script: new light-mode contrast is **4.63–5.46:1**
    across all three light surfaces (passes AA everywhere), dark mode mathematically unchanged.
    Deliberately did **not** touch `Theme.ok`/`Theme.bad`, which have a smaller version of the same
    gap — out of the reported scope, noted in `ideas.md` instead.
  - **Truncation bug:** the Queue row's name `Text` (`QueuePanel.swift:267`) had a hardcoded
    `.frame(width: 220)`. Its sibling — `CJProgressBar` (a `GeometryReader`) for active jobs, or a
    bare `Color.clear.frame(height: 5)` placeholder for pending ones — has no width constraint and
    is SwiftUI's single "greediest" child in that `HStack`, so it silently absorbed all of the row's
    spare width instead of the name, which is why the row visibly had room but still truncated.
    Fix: `.frame(minWidth: 220, maxWidth: 420, alignment: .leading)` — bounded, not fixed.
  - Clean build succeeded (`xcodebuild` clean → build, per this project's protocol).
  - **Verification hit two environment gaps:** `screencapture` has no Screen Recording permission
    in this sandboxed shell (can't take pixel screenshots), and the AppProbe binary the `/test-app`
    skill references (`~/ProgrammingProjects/9-TESTING/AppProbe`) isn't installed on this Mac.
    Worked around both: generated a synthetic DJI fixture clip with the bundled `ffmpeg`
    (`mpeg4`, correct `creation_time`), then drove the running app end-to-end via
    Accessibility (`System Events`) UI scripting — scan → select → toggle rename → read live
    preview → add to queue → measure the actual rendered queue-row width via the accessibility
    tree. A 49-char synthetic output name rendered at **346pt** (fits the new 420pt cap, full
    string, no truncation) vs. the old hardcoded 220pt cap that would have clipped it.
  - Cleaned up afterward: quit the test app instance, reset `~/Library/Application
    Support/Conjoyn/queue.json` to `[]` (Debug and Release builds share this file, and it held
    only the two synthetic test jobs — no real prior data was visible in it), deleted the scratch
    fixture files.
  - Branched `fix/ui-polish-rename-contrast-queue-width` off `main`, committed, fast-forward merged
    to `main` (`ee0092d`), branch deleted. `docs/ideas.md` entries marked `✅ RESOLVED 2026-07-04`.

## Decisions
- Scoped the contrast fix to `Theme.acc1` only, not `Theme.ok`/`Theme.bad` (which measured a
  smaller but real version of the same light-mode gap) — the user reported one specific instance;
  fixing the shared token that instance uses was justified root-cause work, but widening to two
  more tokens nobody flagged would have been unrequested scope creep. Logged as a flagged-but-
  deferred item in `ideas.md` instead of silently fixing or silently ignoring it.

  asked "could this be fixed now and deployed?") — recommended holding it for the next real
  release (GoPro/Osmo Action work) rather than running the full notarize + appcast + lftp cycle
  for two cosmetic tweaks. User agreed by proceeding with "fix it" rather than "ship it."
