### The cold review is the story of this session

The two feature commits were green, falsified, and looked done. A `code-reviewer` agent read the diff
without the reasoning that produced it and returned **changes-requested** — 0 critical, 0 high, 4
medium, 3 low — having **confirmed the important findings by experiment rather than by reading**.
Four of them were the same failure shape, and it is the exact shape this wave exists to prevent:
**green when it should be red.**

1. **The output index was arithmetic, not a lookup.** It was computed as `hasAudio ? 2 : 1` from the
   join's `-map 0:v:0 -map 0:a? -map 0:<i>` order. The reviewer ran the real join and found that
   **`-map 0:a?` maps *all* audio streams** — so a two-audio-track source puts gpmd at index 3 while
   the formula says 2, and the check would compare gpmd against audio and hard-fail a byte-perfect
   join. Worse, the unit "test" for it *restated the formula* (tautological), and the fixtures happen
   to put gpmd at index 2 on both sides, so nothing in the suite could have caught it. Now probed
   directly — which also turns "the join dropped gpmd" into a **named** failure instead of a silently
   skipped check.
2. **A job with an unresolvable layout sealed green.** `streamInfo` is populated with `try?` at
   discovery, while the join resolves the index freshly at join time. So a GoPro job whose discovery
   probe hiccupped would **join with telemetry and then verify with no telemetry check at all**,
   reporting "All checks passed". Now emits a `.warning` ("telemetry not verified — stream layout
   unknown") that also auto-escalates to Tier 2. DJI jobs stay silent.
3. **The seal laundered a telemetry failure.** `mapStatus` lets a passing Tier-2 hash forgive Tier-1
   deltas — sound reasoning, but only for streams the hash actually covered, which is exactly why
   `tmcd` already had a carve-out. When telemetry is missing, Tier 2 falls back to hashing v/a only,
   so a dropped-telemetry join failed Tier 1 loudly, auto-escalated, and then sealed `.verified`.
   Reproduced through a real `.drop`-policy join of the Hero 11 fixtures before fixing. `gpmd` now
   shares `tmcd`'s carve-out, for the same reason, stated in the same comment.
4. **And that carve-out read only the first gpmd check** — found by reading the fix, not by the
   review. The telemetry stream emits **two** `.gpmdParity` checks (count and bytes, as video and
   audio do), so `first` inspected only the count verdict and would launder a bytes-only failure.
   That is precisely how corruption presents when the packet count survives but the payload doesn't.

Every fix was falsified: revert it, confirm the matching test goes red, restore, re-run. Finding 4's
falsification printed `got verified` on the reverted build — the bug, reproduced on demand.

## Decisions

Full entry in `decisions.md` (2026-08-09, "The telemetry check is verified by absolute index, and its
new kind is a one-way door"). In brief:

- **Absolute index, never `d:0`, resolved separately per side.** `d:0` selects whichever data stream
  is first, which on a GoPro camera original is the `tmcd` timecode track — a *passing* check that
  verified the wrong stream. Both sides match on `codec_tag_string == "gpmd"`.
- **Reversed mid-wave:** the output index is **probed, not derived** (see finding 1).
- **Accepted with eyes open:** `gpmdParity` is the first new `VerificationCheck.Kind` since shipping.
  G0.3's tolerant decoder protects builds from that point onward, but **1.0.4 predates it**, so a
  queue written by this build and read by a *reinstalled* 1.0.4 throws and the catch discards the
  user's entire queue. The downgrade-safe alternative (reuse `packetCount`/`packetBytes`, carry
  gpmd-ness only in the label) was rejected as making the telemetry verdict indistinguishable from a
  video one in code, for a path that needs a manual older-DMG reinstall.
- Named, not fixed: the case is `gpmdParity`, not `telemetryParity`, because
  `QueuePersistenceCompatTests` already uses that literal as its unknown-kind fixture — the obvious
  name would have turned a protected test's placeholder into a real decodable case.

**The rule (G6.1).** A GoPro chapter is final when its size is below **0.94×** the smallest
*preceding* chapter of the same recording. The existing 4-argument `isComplete` is left byte-for-byte
untouched and the new family-aware overload **delegates to it verbatim** for `.dji` — so the DJI
verdict is unchanged by construction rather than by assertion, and `CompleteSetGateTests` needed
**zero edits**. New settings fields `goProSplitFloor` / `goProFinalChapterRatio` follow the file's
existing `CodingKeys` + `decodeIfPresent` pattern.

**Both constants were measured before any code was written**, from the 71-file corpus already pinned
in `DJIFolderGroupingTests` (its `CorpusRow` / `corpusRows` had `private` removed so the gate test
could reuse them — deliberately *not* duplicated, since two copies would drift):

| | final chapters | non-final |
|---|---|---|
| ratio to min(preceding) | 0.0762 – **0.8850** (6348 ch03) | **0.99989** – 1.00015 |

That ~11-point gap puts 0.94 roughly in the middle, and it forces a **strict `<`** — a non-final
ratio can *exceed* 1.0 when a later chapter is marginally larger than the smallest earlier one.

## Decisions

- **The plan's no-reference rule was a regression, and was replaced.** The task said "with only one
  member and no reference, the quiet window alone decides". True for a genuine single-chapter
  recording — but mid-copy a 4-chapter recording *is* a one-member group, only chapter 01 having
  landed. That rule would pass an 11.5 GB chapter 01 after 45 s of quiet and join it **alone**,
  producing a truncated output plus an orphan group. The shipped absolute rule blocks that correctly
  (11.5 GB > 3.9 GB), so following the plan would have made GoPro watch-folder behaviour *worse than
  1.0.4*. Resolved by user decision: a **9.5 GB no-reference floor**, sitting in the corpus's wide
  empty band (largest true single 7.66 GB · smallest cap-filled chapter 11.4976 GB). Knowingly
  reintroduces a constant that decision Q3 wanted to avoid — accepted, because the alternative is a
  premature join. Rejected: falling back to the existing 3.9 GB `splitThreshold`, which would stall a
  real 7.66 GB single-chapter recording forever.
- **A stray zero must not poison the reference** (hardened past the task text). Non-positive
  preceding sizes are filtered out *before* `min()`. A bare `min()` did two bad things at once: made
  the ratio comparison `x < 0` — never true, stalling the group forever — and discarded a genuine
  reference sitting beside the zero, falling to the floor branch, which for a 9 GB last chapter flips
  the verdict from "wait" to "join now". Filtering errs toward "expect continuation", the safe
  direction. Defensive only: `FileStabilityGate.isSettled` requires
  `samples.count >= requiredStablePolls`, so an unsampled clip fails Gate 1 first — confirmed by
  reading the guard, not assumed.
- Both entries written up in full in `decisions.md` (2026-08-09).
