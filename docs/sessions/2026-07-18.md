# Session: 2026-07-18

## Goal
Diagnose and fix a user-reported crash in shipped 1.0.3: changing the output folder while
pending jobs sat in the queue killed the app (EXC_BREAKPOINT via
`+[NSApplication _crashOnException:]`, macOS 27.0 beta 26A5378n, M4 Pro).

## Progress
- **Root-caused from the crash report alone** (no debugger needed — the backtrace told the
  whole story): `chooseOutputFolder()` set `showApplyFolderPrompt = true` synchronously
  after `NSOpenPanel.runModal()` returned. On macOS 26+ the open panel is
  **ViewBridge-hosted** (its content is an out-of-process `NSRemoteView`, even for
  unsandboxed apps). Flipping the `@Published` flag in the same runloop turn made SwiftUI
  present the `ApplyFolderPopover` while the panel's remote view was still mid-teardown
  over XPC — the popover's window ordering posted a notification that the dying remote
  view's stale observer (`containingWindowWillOrderOnScreen:`) received, it threw, and
  AppKit's crash-on-exceptions trapped. Repro: add all groups from
  `2JOIN-IN/IN-M2A/DJI-M2A--2026-07-13/100MEDIA` to queue → change output folder to
  `2CULL-IN/IN-M2A` → crash.
- **Fix** (`ConversionViewModel.swift:293`): defer the flag flip past the teardown —
  `Task { try? await Task.sleep(for: .milliseconds(400)); showApplyFolderPrompt = true }`.
  Class is `@MainActor`, so the unstructured Task inherits main-actor isolation; a bare
  `main.async` is NOT enough because the teardown spans XPC round-trips. Why-comment left
  in code so the delay doesn't get "simplified" away.
- **Sibling audited, no change:** `WatchFoldersPanel.swift:86` also runs an `NSOpenPanel`,
  but its settings popover is user-toggled, never auto-presented after dismissal.
- **Verified:** clean xcodebuild cycle → BUILD SUCCEEDED; user re-ran the live repro in
  the debug build → **no crash** (race-class bug, so: one clean run + fully understood
  mechanism = high confidence, not absolute proof).
- **Committed `dcf44b8` to `main` + pushed.** Same commit gitignores `.claude/logs/` and
  `WORKING_NOTES.md` (session-local noise that was showing as `?? .claude/`).

## Decisions
- Tactical fix only (timing deferral), not a migration of `runModal()` →
  `begin(completionHandler:)` — the async-panel API would still need the same deferral, so
  it buys nothing for this bug. Not decisions.md-worthy.

## Next
- **Ship rides the next planned version update** (user call) — the fix exists only in
  source/debug until then; installed `/Applications` build is still crashing 1.0.3.
  When cutting it: bump `project.yml` → 1.0.4/104 and follow the verified ship recipe in
  PROJECT_STATE Infrastructure.

# Session 2: 2026-07-18 — Saved rename templates

## Goal
Build the user's feature idea: the Rename popover should be able to store rename templates
(reusable custom patterns that survive relaunch — `renameOptions` is deliberately session-only,
so a custom pattern previously had to be retyped every launch).

## Progress
- **Explored per the UI-changes protocol first** (found the comparable control, traced wiring,
  proposed placement, got confirmation): preset chips in `RenamePopover.swift` already carry the
  recall + selected-highlight mechanics (`vm.renameOptions.pattern == chip.pattern`), so a saved
  template is just a stored pattern string — no "active template" state needed anywhere.
- **User design calls:** templates capture the **pattern only** (counter start/digits stay
  per-batch, matching the built-in presets and the 2026-06-10 counter-restarts-per-batch
  decision); chips are **labelled with the pattern itself** in monospace — zero naming UI.
- **Built:** new `Models/RenameTemplates.swift` — Codable blob under one UserDefaults key
  (`rename.templates`), the `WatchFolderSettings` load/save idiom (corrupt blob ⇒ empty);
  `add` (trim + dedup), `remove`, `canSave` (rejects empty / built-in presets / already-saved).
  In `RenamePopover.swift`: a "Saved:" chip row between Preset and Pattern (hidden until the
  first save), a ＋ chip that only exists while the current pattern is savable (so a visible ＋
  always does something; it sits in the Preset row while Saved is empty), right-click →
  Delete Template, and a minimal `ChipFlowLayout` (SwiftUI `Layout`) so arbitrarily-wide pattern
  chips wrap inside the fixed 430 pt popover. `xcodegen generate` for the two new files.
- **Tests:** +13 (`RenameTemplatesTests`) — add/trim/dedup, remove, canSave rules, UserDefaults
  round-trip, corrupt-blob fallback. **488 / 1 skip / 0 fail** (was 475; no regressions).
- **Live verification:** AX scripting proved too flaky to drive the popover (learning captured —
  see Decisions), but the app's real UserDefaults blob proved the save path fired end-to-end in
  the running debug build, and the user then eyeballed all four steps — Saved row appears, chip
  recall fills the field, right-click delete removes it, preset restore — **all PASS**.
- **Merged `--no-ff` to `main` (`f95a44b`), pushed, feature branch deleted.** Tree clean, in sync.

## Decisions
- Templates are pattern-only, labelled by their own text (no naming UI) — logged to
